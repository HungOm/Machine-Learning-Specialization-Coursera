11.9The anomaly detection algorithm

One Gaussian per feature, multiplied together. Four steps, and the multiplication is where the power comes from.

C3 · Week 1 · lesson 9 of 12143 of 177 · 81% of the book

❓Before you read

Each feature alone looks unremarkable — 1.5σ off, nothing dramatic. Guess what happens when a point is 1.5σ off on six features at once.

I have committed to an answer

Watch for the multiplication. Six mild oddities combine into something astronomically unlikely, and that is the whole trick.

🎈The idea, in plain words

In plain English

You check each thing separately. Is the temperature odd? A bit. Is the vibration odd? A bit. Is the noise odd? A bit.

Now here is the trick: you multiply the “not odd” chances together. Being slightly unusual in one way is common. Being slightly unusual in five ways at once is very rare — because 0.3 × 0.3 × 0.3 × 0.3 × 0.3 is tiny.

🔢The maths, decoded

multiply the per-feature probabilities together — hover or click a part
p(x)a number from 0 to 1 = Πj=1nmultiply every feature's probability p(xj; μj, σj2)
SymbolSay it out loudWhat it actually is
Π“product over j”Like Σ but multiplying instead of adding. Capital pi.
p(xj; μj, σj²)“the Gaussian for feature j”Each feature gets its own μ and σ, fitted independently. The semicolon means “parameterised by”.
n“how many features”Two in the pictures, eleven in the assignment, dozens in practice.
independence“the assumption”The product formula assumes the features are statistically independent. They usually are not — and it works well anyway.
🔧If you have never seen a formula

A mechanic who knows what a healthy engine sounds like.

He cannot list every possible fault — he has never heard most of them. What he has is a very precise sense of normal, and anything outside it makes him stop and listen. He detects faults he has never encountered, purely by knowing normal well.

🌉If you know a neighbouring field

This is density estimation, and it is fundamentally different from classification: you model P(x) rather than P(y | x).

Fit a Gaussian per feature, multiply the per-feature probabilities, and flag anything improbable. The multiplication is the key design choice — it means one sufficiently strange feature can condemn an example even when everything else looks ordinary.

👁One thing to picture

A dartboard of normal readings with a wide, fuzzy edge.

Most points land in the dense middle. The threshold ε draws a contour around the crowd — inside is normal, outside is flagged. Move ε outward and you flag less; inward and you flag more, including some perfectly ordinary points in the tails.

⚖️Where this really costs something

This is how credit-card fraud detection works, and why it must: fraudsters invent new methods constantly, so a classifier trained on last year’s fraud is trained on the wrong thing.

Modelling normal catches novel attacks a classifier never could. That is the real reason to choose this over supervised learning — not the class imbalance, but the fact that future positives will not resemble past ones.

So p(x) < ε below is the whole decision rule, and the honest work is in choosing ε and choosing features.

🎬Watch it move

▶ Two features, one product, one thresholddrag ε and watch which points get flagged

🔢The four steps

  1. Choose features x₁ … xn that you think might expose an anomaly.
  2. Fit each one: μj = mean of that feature, σj² = its variance. n Gaussians, fitted independently.
  3. For a new x: compute p(x) = Πj p(xj; μj, σj²).
  4. Flag it if p(x) < ε.
The one thing to remember

The multiplication is what makes this work. A point that is 1.5σ off on one feature is unremarkable. A point that is 1.5σ off on six features simultaneously has a p(x) hundreds of times smaller — even though no single feature looked alarming.

💻In code

def estimate_gaussian(X):
    mu  = X.mean(axis=0)                 # one mean per feature      -> shape (n,)
    var = X.var(axis=0)                  # one variance per feature  -> shape (n,)
    return mu, var

def multivariate_gaussian(X, mu, var):
    # product over features, computed for every row at once
    p = np.exp(-((X - mu) ** 2) / (2 * var)) / np.sqrt(2 * np.pi * var)
    return np.prod(p, axis=1)

mu, var = estimate_gaussian(X_train)     # normal examples only
p = multivariate_gaussian(X_cv, mu, var)
anomalies = p < epsilon
Watch out

With many features the product underflows: 30 probabilities of 0.1 each multiply to 10⁻³⁰, and with more features you eventually hit exactly 0.0 in floating point. The standard fix is to work with log p(x) = Σ log p(xj) — sums instead of products. Same ranking, no underflow. This is the same numerical-stability lesson as C2 W2 L9.

🕳Traps

Common trap

A feature with variance 0. Division by zero, and p becomes NaN or infinite. Happens when a column is constant. Drop the feature, or add a tiny epsilon to the variance.

Common trap

Worrying about the independence assumption. It is technically wrong almost always, and the algorithm works regardless. If correlated features genuinely matter, the multivariate Gaussian (with a full covariance matrix) is the extension — at the cost of needing far more data.

Say it out loud

The independence assumption is “technically wrong almost always” and the algorithm works anyway. Say why being wrong is survivable here.

said it — now check

Because you are not trying to model the distribution accurately — you are trying to rank examples by how unusual they are. A model can be badly calibrated and still put the strange things at the bottom of the list, which is all ε needs.

It fails specifically when the anomaly is only visible in the correlation — high CPU with low traffic, where each feature alone is unremarkable. That case needs a full covariance matrix, or an engineered ratio feature, which is the cheaper fix.

✅Check yourself

Three features, each with p = 0.1 for this example. What is p(x)?

0.1 × 0.1 × 0.1 = 0.001. Each feature alone was only mildly unusual; together they are a thousand-to-one shot.

Why does p(x) get smaller as you add more features, even for normal examples?

Because you are multiplying more numbers below 1. This means ε must be re-tuned whenever you change the feature set — it is not transferable.

What does the independence assumption actually claim?

That knowing one feature tells you nothing about another. Rarely true — CPU load and network traffic move together — but the algorithm tolerates it well.

    On a fleet of 1,000 normal servers (traffic and CPU move together), the independent model misses the stuck server above. An engineer's fix:

    1. Compute p(x) for the stuck server.
    2. Set ε just above it, so the stuck server is flagged.
    3. Ship it.

    Which line is wrong?

    show me where it breaks

    Line 2. ε is one dial for every example. Raising it to catch this server also flags 14.2% of the normal fleet, because the model ranks those normal servers as less probable than the broken one. The missing signal is not a threshold problem; the model cannot represent it.

    Add the ratio feature: the stuck server's ratio is 40σ out, while the most extreme normal server is 3.6σ out. It can be caught with no false alarms.
