🔢Why scaling is not tidying

The same thing with numbers small enough to check

Three houses, three features. Look at what the raw columns actually span, then at what they span after scaling.

size, raw range1252square feet
bedrooms, raw range3a count
age, raw range10years
size μ, σ1457.333, 511.962computed on the training set only
size, scaled range2.445
bedrooms, scaled range2.405
age, scaled range2.449all three now comparable
2104 sq ft becomes1.2631just over one standard deviation above average

Size spans 1252 and bedrooms spans 3 — a ratio of about 417 to 1. One shared learning rate cannot suit both: a step small enough not to diverge on size is far too small to move bedrooms at all. After scaling all three spans are within 2% of each other, and one α works for everything.

⛓The two genuinely new ideas

The pieces, in the order they hand to each other
  1. 1Vectorization

    Replace the loop over features with a dot product. Same maths, same answer, dramatically faster.

    the same thing in code
    f = X @ w + b        # not: for j in range(n): ...

    where it goes wrongIt is not “NumPy is clever”. The loop pays Python interpreter overhead per element; @ hands one contiguous block to compiled code that uses SIMD — one instruction multiplying several pairs at once — and often several cores. 10–100×, and the same reason GPUs matter.

    ↓a model that can handle hundreds of features without the code getting longer.

  2. 2Feature engineering

    Compute a new column yourself and hand it over, because the model cannot invent it.

    the same thing in code
    X3 = X1 * X2          # area = frontage x depth

    where it goes wrongA linear model is a weighted sum. There is no choice of w₁ and w₂ that produces a product — it is outside what the model can represent, so no amount of data or training will find it.

    ↓and if the new column is a POWER of an old one, you get curves.

  3. 3Polynomial regression

    Feed it x, x², x³ and it fits a curve — while remaining, in every technical sense, linear regression.

    the same thing in code
    X = np.c_[x, x**2, x**3]

    where it goes wrong“Linear” means linear in the parameters w, not in x. But if x runs 1–1000 then x³ runs 1–1,000,000,000, which makes scaling mandatory rather than merely advisable.

📉The cheapest diagnostic in machine learning

The one thing to remember

Plot J against iteration number. Three lines of matplotlib, and it diagnoses four situations by eye:

Falls then flattens → converged; stop. Falls, still falling → run it longer. Oscillates → α too large; reduce it. Increases steadily → α far too large, or a bug.

And the rule that never fails: if J ever increases between two iterations, α is too large. To choose α, try a ladder roughly ×3 apart — 0.001, 0.003, 0.01, 0.03, 0.1 — and keep the largest one that still falls smoothly. ×3 rather than +0.1 because α acts multiplicatively, so equal ratios matter, not equal differences.

🚧The two scaling traps

Common trap

Scaling before splitting. Compute μ and σ on the whole dataset and you have leaked test information into training. Your test score comes out optimistic and nothing tells you.

Forgetting to scale at prediction time. The model was trained on standardised inputs. Feed it a raw 2000 and it returns nonsense — with no error, because 2000 is a perfectly valid number.

One rule prevents both: fit the scaler on the training set only, then apply those same numbers everywhere — validation, test, and every future prediction. That is exactly why sklearn separates fit from transform.
