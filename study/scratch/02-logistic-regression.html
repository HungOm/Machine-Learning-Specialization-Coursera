The textbook 1/(1+np.exp(-z)) overflows for very negative z, because e^1000 does not fit in a float. The two branches here are algebraically identical and each avoids the overflow the other would hit. Libraries all do some version of this; it is worth seeing once.

def sigmoid(z):
    """1 / (1 + e^-z), written so it never overflows.

    For very negative z, e^-z is astronomically large and np.exp warns.
    The two branches are algebraically identical; each avoids the overflow
    the other would hit.
    """
    z = np.asarray(z, dtype=float)
    out = np.empty_like(z)
    pos = z >= 0
    out[pos] = 1.0 / (1.0 + np.exp(-z[pos]))
    ez = np.exp(z[~pos])
    out[~pos] = ez / (1.0 + ez)
    return out

print("sigmoid(-1000) =", sigmoid(-1000.0), " (no overflow warning)")
print("sigmoid([-2, 0, 2]) =", np.round(sigmoid([-2, 0, 2]), 4))
print("g(-z) == 1 - g(z):", np.allclose(sigmoid(-3.7), 1 - sigmoid(3.7)))

This is the one genuinely new idea in the file. The weighted sum can come out as any number at all. A probability may not — it has to sit between 0 and 1. The sigmoid is the funnel between them.

  1.0 |                        _____----------
      |                  __--
      |               _--
  0.5 |- - - - - - - -*
      |            _--
      |       __---
  0.0 |------
      +----------------------------------------
           negative        0        positive
                        z
Very negative goes to 0, very positive goes to 1, and it passes through exactly 0.5 at z = 0.

Notice it is symmetric: 0.1192 and 0.8808 add to exactly 1. That is the last line of the output checking itself — the chance of passing at z and the chance of failing at −z are the same number.

Now, why is the function written in two halves? The textbook formula is one line:

1 / (1 + exp(-z))the version in every textbook, and it breaks

Try it at z = −1000. The machine has to work out exp(1000) — a number with 435 digits. It does not fit in a float. It overflows and warns, and you get nonsense.

so the code splits in two, and each half is safe where it is used
When z is 0 or above
1 / (1 + exp(-z))
The exponent −z is negative or zero, so exp stays small and safe.
When z is below 0
exp(z) / (1 + exp(z))
Now the exponent z is the negative one, so again exp stays small and safe.
The pointThese are not two different formulas. Multiply the top and bottom of the first by exp(z) and you get the second exactly. Same maths, rearranged so that whichever side of zero you are on, the thing being exponentiated is never positive.

You will meet a second spelling of this. File 03 writes it as a single np.where. It is not a different sigmoid — the two agree to the last bit over 20,001 values from −800 to +800, and at ±10,000 too.

But it is safe for a different reason, and the difference is worth knowing. np.where does not pick a branch and skip the other: it computes both branches over the whole array, then chooses element by element. So putting the obvious two formulas inside an np.where would still overflow — the doomed half runs anyway. File 03 uses -|z| in both branches, which is never positive whichever side you are on.

same answer, two different ways of avoiding the same cliff
This page's version is safe because…
each formula only ever runs on the half of the data it suits.
File 03's version is safe because…
neither formula can overflow in the first place.

Two details. np.clip keeps the log away from 0, where it would return −inf. And the penalty is on w only — never on b, because shrinking the model's baseline towards zero buys nothing.

def compute_cost(X, y, w, b, lam=0.0):
    """Average log loss, plus the regularization term on w only (never b)."""
    f = sigmoid(X @ w + b)
    eps = 1e-12                                  # keeps log() away from 0
    f = np.clip(f, eps, 1 - eps)
    loss = -(y * np.log(f) + (1 - y) * np.log(1 - f))
    return float(loss.mean() + (lam / (2 * len(y))) * np.sum(w ** 2))
Line by line, in plain words

The cost answers one question: how bad is this set of weights? One number, so that two candidate models can be compared.

File 01 squared the miss. That will not do here. Suppose the model says “99% sure this student passed” and the student failed. The plain error is 0.99, which sounds small. It is a catastrophe, and the cost has to say so.

the log lossloss = -( y * log(f) + (1 - y) * log(1 - f) )“minus, y times log f, plus one minus y times log one minus f”

It looks forbidding and it is really two cases wearing one coat. Because y is always 0 or 1, one of the two halves is always multiplied by zero and disappears.

one of these two is always zero
If the student PASSED  (y = 1)
1 - y is 0, so the right half vanishes.
Only -log(f) is left.
If the student FAILED  (y = 0)
y is 0, so the left half vanishes.
Only -log(1-f) is left.
the student passed. What each guess costs
said 0.99→cost 0.01confident and right — almost free
said 0.60→cost 0.51unsure — charged a little
said 0.01→cost 4.61confident and wrong — 460× more
The pointRight and confident is nearly free. Unsure costs a little. Wrong and confident costs enormously — and the cost runs off towards infinity as the model approaches total certainty about something false. That asymmetry is not a side effect. It is the entire reason this cost exists instead of the squared error.

Which is also why the next two lines are there:

eps = 1e-12 f = np.clip(f, eps, 1 - eps)keep f away from the cliff edges

log(0) is undefined — it heads for minus infinity — so a probability that rounds all the way to 0 or 1 would poison the whole sum. np.clip nudges them to 0.000000000001 and 0.999999999999: far enough from the edge to be safe, close enough to change no answer you care about.

The last term is the fine for large weights:

(lam / (2 * len(y))) * np.sum(w ** 2)λ times how big the weights have grown
The pointNotice what is not in that term: b. The bias is never penalised. Shrinking w flattens the model’s confidence, which is the point; shrinking b would only drag the boundary towards the origin, for no reason at all.

Compare this line with the linear-regression version: (X.T @ err) / m. Character for character the same. Only the definition of err changed, because a sigmoid's derivative and a log's derivative cancel exactly. That cancellation is the real reason these two are always paired.

def compute_gradient(X, y, w, b, lam=0.0):
    """Character for character the same as linear regression, except f."""
    m = len(y)
    err = sigmoid(X @ w + b) - y
    dj_dw = (X.T @ err) / m + (lam / m) * w      # penalty derivative is (lam/m)w
    dj_db = float(err.sum() / m)                 # b is NOT regularized
    return dj_dw, dj_db
Line by line, in plain words

Here is the payoff for all of file 01. Read these two lines next to the linear regression ones and they are character for character the same:

err = sigmoid(X @ w + b) - y — the only difference in the entire gradient is that sigmoid(...) sits where the bare line used to be. That is not a coincidence or a convenience; it falls out of the algebra, and it is why the log loss is the “right” cost for a sigmoid rather than an arbitrary one.

X.T @ err is the same weighted sum you met in file 01: each student's miss multiplied by that student's scores, added up. .T is the transpose — it turns the table on its side so the shapes line up: (2, 80) @ (80,) → (2,), one slope per weight.

+ (lam / m) * w is the penalty's own slope. A large weight gets a large push back towards zero; a weight already near zero is barely touched.

And dj_db has no lam term at all, matching the cost: b is never regularized.

Same checker as file 01, now with λ switched on, so the penalty's derivative (λ/m)·w is verified too.

def numeric_gradient(f, theta, eps=1e-6):
    g = np.zeros_like(theta, dtype=float)
    for i in range(theta.size):
        up, dn = theta.astype(float).copy(), theta.astype(float).copy()
        up[i] += eps; dn[i] -= eps
        g[i] = (f(up) - f(dn)) / (2 * eps)
    return g

Line by line, in plain words

This block is a test, and it is the reason to trust everything after it.

There are two ways to find a slope. You can do the calculus — that is compute_gradient. Or you can measure it: nudge one weight up by a hair, nudge it down by a hair, see how much the cost moved, and divide. That is numeric_gradient, and eps = 1e-6 is the size of the hair.

The measured version is far too slow to train with — it re-runs the whole cost twice for every single weight — but it needs no calculus, so it cannot repeat a calculus mistake. If the two agree, the derivative was differentiated correctly.

Look at the output. Both come out as [-0.33510702, -0.36844957] and the largest disagreement is 6.785e-11 — a decimal point followed by ten zeros. That is the noise floor of floating-point arithmetic, not an error.

This is a real professional habit, not a teaching exercise. A wrong gradient does not crash. It trains happily and converges to the wrong answer, and this ten-line check is how you find out.

Nothing new — the loop is identical to linear regression.

def gradient_descent(X, y, alpha, iters, lam=0.0):
    w, b = np.zeros(X.shape[1]), 0.0
    for i in range(iters):
        dw, db = compute_gradient(X, y, w, b, lam)
        w, b = w - alpha * dw, b - alpha * db
        if i % (iters // 5) == 0:
            print(f"  iter {i:5d}  cost {compute_cost(X, y, w, b, lam):.5f}")
    return w, b

print("\ntraining (lambda = 0):")
w, b = gradient_descent(Xs, y, alpha=0.5, iters=5000)
print(f"learned w = {np.round(w, 4)}  b = {b:.4f}")
Line by line, in plain words

w, b = np.zeros(X.shape[1]), 0.0 starts every weight at zero. Follow what that means on the first iteration: z is 0 for every student, so sigmoid(0) is 0.5, so the model's opening position is “every student has a 50-50 chance”. It knows nothing, and it says so.

Then the loop, three lines, repeated 5,000 times: work out which way is downhill, step that way, repeat.

Xs = (X - X.mean(0)) / X.std(0), back in the check block, is why it works at all. Raw exam scores run 20–100; after scaling they run about −2 to +2. Without that, one weight needs a big step and the other a small one, and a single alpha cannot suit both.

Line by line, in plain words

The model outputs probabilities. A decision needs a yes or a no, so (prob >= 0.5) draws the line. The comment in the file — “the threshold is a separate choice” — is the important part: 0.5 is not something the model learned. You chose it, and you may choose differently.

.astype(int) just turns True/False into 1/0 so it can be compared with y.

The four counts are the four things that can happen, and they are worth saying slowly. Treating “passed” as the positive case:

  • TP = 38 — said pass, did pass. Correct.
  • TN = 38 — said fail, did fail. Correct.
  • FP = 2 — said pass, actually failed. A false alarm.
  • FN = 2 — said fail, actually passed. A miss.

Precision = 38/(38+2) = 0.95: when it says pass, how often is it right? Recall = 38/(38+2) = 0.95: of everyone who really passed, how many did it find? They are equal here only because FP and FN happen to both be 2. F1 combines them into one number, and it is 0.95 too.

Accuracy is 0.95 as well — 76 right out of 80. It agrees with the others here because the classes are balanced, forty and forty. On a lopsided problem it stops agreeing, and that is precisely when precision and recall earn their keep.

The boundary is wherever z = 0, because g(0) = 0.5. You never compute a sigmoid to find it — solve the straight line instead.

# The boundary is where z = 0, i.e. w1*x1 + w2*x2 + b = 0.
# Solve for x2:  x2 = -(w1*x1 + b) / w2
print("\ndecision boundary in scaled space:")

Line by line, in plain words

Where exactly does the model change its mind? At the probability 0.5. And sigmoid gives 0.5 at exactly one input: z = 0.

So the dividing line is wherever w₁x₁ + w₂x₂ + b = 0. Rearranging for x₂ gives the line the code prints: x₂ = -(w₁x₁ + b) / w₂.

Three points off that line appear in the output: at x₁ = −1 the boundary is at x₂ = +1.690; at x₁ = 0 it is at +0.033; at x₁ = +1 it is at −1.623. Three points, dropping steadily — it is a straight line, sloping down.

Which is the honest limit of this model. Everything on one side is called a pass, everything on the other a fail, and the frontier between them is straight. It cannot curve around an island of failing students sitting in the middle of the passing ones.

These numbers are in scaled space, because the model was trained on scaled data. To draw the line on a chart of real exam marks you would have to undo the scaling first.

Line by line, in plain words

This block runs the whole training four times with a bigger λ each time, and prints two things: how big the weights got, and how accurate it was.

np.linalg.norm(wl) is the length of the weight vector — roughly “how big are all the weights together”. Read the column down:

  • λ = 0 → |w| = 5.52, accuracy 0.950
  • λ = 1 → |w| = 2.93, accuracy 0.963
  • λ = 10 → |w| = 1.28, accuracy 0.963
  • λ = 100 → |w| = 0.32, accuracy 0.963

The weights shrink by a factor of seventeen and the accuracy goes up and stays up. That is the argument for regularization in four lines: the same decisions, made with less confidence, and the confidence was never earned in the first place.

What is actually happening: with λ = 0 nothing stops the weights growing, so the model pushes every probability towards 0.000 or 1.000 — it becomes certain. λ charges a fee for that certainty. The boundary stays in nearly the same place; the model just stops shouting about it.

Now the trap. The regularized update is w := w(1 − αλ/m) − α·gradient, so it shrinks w by a factor before every step. If αλ/m > 2 that factor goes past −1 and the weights flip sign and grow every iteration. A λ that is perfectly safe at one α diverges at another — and this is not in any lecture.

# Regularized descent shrinks w by (1 - alpha*lam/m) before every gradient step.
# If that factor goes negative, w flips sign and grows every iteration. This is
# a real trap: a lambda that is fine at one alpha diverges at another.
print("\nthe hidden constraint between alpha and lambda:")
print(f"{'alpha':>7} {'lambda':>7} {'1-a*l/m':>9}   outcome")
for alpha, lam in [(0.5, 100.0), (0.5, 320.0), (0.5, 1000.0), (0.05, 1000.0)]:
    factor = 1 - alpha * lam / m
    wl, bl = np.zeros(n), 0.0
    with np.errstate(over="ignore", invalid="ignore"):   # divergence is the point here
        for _ in range(2000):
            dw, db = compute_gradient(Xs, y, wl, bl, lam)
            wl, bl = wl - alpha * dw, bl - alpha * db
        norm = np.linalg.norm(wl)
    state = "diverged" if not np.isfinite(norm) else f"|w| = {norm:.4f}"
    print(f"{alpha:7.2f} {lam:7.0f} {factor:9.3f}   {state}")
print("\nStable only while alpha*lambda/m < 2, i.e. alpha < 2m/lambda.")
print(f"With m = {m} and lambda = 1000 that means alpha < {2*m/1000:.3f}.")
Line by line, in plain words

The last block is the trap, and it is not in any lecture.

Look at what the regularized update does to w before the gradient is even applied. Combining the two terms gives w := w(1 − αλ/m) − α × gradient. So every step multiplies the weights by 1 − αλ/m. Call that the shrink factor.

  • factor 0.9 → the weight gently shrinks: 10 → 9 → 8.1. Fine.
  • factor −0.5 → the weight flips sign every step: 10 → −5 → 2.5. Ugly, but still shrinking.
  • factor −5.25 → it flips and grows every step. Gone.

The output walks straight through those cases. α = 0.5 with λ = 100 gives a factor of 0.375 and settles at |w| = 0.32. Push λ to 320 and the factor hits exactly −1.000, which is the knife edge: it does not blow up but it does not settle either, ending at |w| = 538. At λ = 1000 the factor is −5.25 and it diverges.

Then the last line of the block fixes it without touching λ at all: keep λ = 1000 and drop α to 0.05, and the factor is back to 0.375 and the weights land at 0.041.

So the rule: you are safe while αλ/m < 2, that is α < 2m/λ. With m = 80 and λ = 1000 that means α must be below 0.160.

The lesson to carry: α and λ are not independent knobs. A λ that is perfectly safe at one learning rate destroys the model at another, and the failure looks like “training diverged”, which sends most people hunting for a bug in the gradient.
